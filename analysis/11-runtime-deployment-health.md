# Runtime topology, deployment, health checks, and testnet preparation

Status: added at Rodrigo's request on October 15, 2026. Extends earlier specifications. Anvil remains the delivery target. Prepare Sepolia configuration/instructions, but do not broadcast or verify on a public network during implementation without an explicit subsequent request.

## Exact running components

1. Anvil: separate local OS process, default RPC http://127.0.0.1:8545, chain ID 31337. Executes transactions, maintains blocks/receipts/logs, and answers JSON-RPC. It does not write our SQLite DB.
2. Deployment script: short-lived Forge Solidity Script, invoked by the local supervisor; deploys contracts, waits for successful receipts, and writes a network-specific deployment manifest through a wrapper. It exits after deployment; it is not the listener.
3. API/indexer: one long-running Node.js OS process, managed by the supervisor. Fastify HTTP server and serialized ingestion worker share this process, with distinct modules. The worker owns writes to SQLite. The HTTP layer reads a consistent DB snapshot; it does not insert escrow changes or sign transactions.
4. SQLite: an embedded library and database file, not a separate database daemon or network service. Startup applies versioned schema migrations before ingestion/HTTP readiness. Foreign keys enabled; journal/projection/checkpoint share the same transaction.
5. Demo/smoke client: separate short-lived TypeScript process, signs only with known local Anvil development accounts. Sends transactions through RPC and queries HTTP for asserted results.

Logical module responsibility (names may vary consistently): api/src/indexer/worker.ts schedules serialized catch-up; api/src/chain/reader.ts fetches headers/logs using ethers; api/src/indexer/projector.ts maps decoded events into record changes; api/src/db/repository.ts owns the atomic SQL transaction; api/src/routes/health.ts reports runtime/DB state. README must describe actual final paths and entry points.

## Listening and write path

- A caller sends a transaction to Anvil. Execution of an Escrow action emits an event; successful receipt logs belong to its containing block. A reverted transaction contributes no committed state-change event.
- Node.js uses ethers JsonRpcProvider over HTTP with block-event polling (explicit polling configuration and documented interval). This is not an inbound blockchain connection to our server and does not require a WebSocket service.
- Register provider.on('block', requestCatchUp). Also run an initial catch-up at startup and a 2-second fallback timer. The timer and callbacks only schedule one worker; coalesce triggers while it is active and recheck pending work before going idle.
- Worker reads head/checkpoint and confirmation cutoff, validates committed chain identity, fetches contiguous headers and provider.getLogs filtered by contract/events, decodes with generated ABI, validates and sorts logs.
- For each validated batch, repository opens one SQL transaction, persists scanned headers and newly seen journal entries, calls projector for only those new events, updates escrows and checkpoint, then commits. On error it rolls back. Fastify reads become able to see the committed snapshot.
- After catch-up, the worker remains alive/idle awaiting notifications or timer. Receiving a notification is never itself proof that the corresponding event was committed.
- Shutdown removes listeners/timers, finishes or rolls back the active batch, closes DB and provider resources, and exits. No orphan listeners or duplicate worker on restart.

Creation projects a new Pending escrow; each terminal event updates state and resolution metadata. Creation/terminal logs are not generated by a DB polling job. Time-derived expiry can change at the next indexed block timestamp even if no Escrow event occurred; headers/checkpoint must therefore advance through empty blocks.

## Required readiness and diagnostics commands

Target commands (to be implemented and verified):

- npm run healthcheck: read-only full-stack diagnostic; terminal PASS/WARN/FAIL table plus overall result, nonzero exit on failed required checks.
- npm run healthcheck -- --json: machine-readable report.
- npm run healthcheck -- --report <path>: optional persisted JSON report with the same checks. Never log RPC credentials/private keys; show sanitized endpoint identity.
- npm run smoke: explicitly state-changing LOCAL ONLY create-and-cancel round trip, proving the live event-to-DB-to-API path; reject chain IDs other than 31337 and use only Anvil fixture accounts/tokens. No automatic state-changing action inside GET /health or ordinary healthcheck.

Healthcheck checks:

1. Config/manifest parse, selected network, RPC contact, actual chain ID/genesis agreement. Check pinned artifact/ABI manifest identity; no unrelated ABI/address file.
2. Deployment receipt success, contract address, deployment block hash, and nonempty runtime code. Compare Escrow runtime bytecode hash against artifact/manifest where applicable (account for actual linking/immutable/compiler metadata if present; don't assert a false generic equality). Verify read-only interface with a known constant getter; do not require a preexisting escrow.
3. Demo ERC-20 code/address for the local profile. No production keys required.
4. API response reachable with matching chain/contract identity. Schema migrations/database readable; report schema version. DB diagnostics must come from the owning API process to avoid creating an empty DB at a wrong path.
5. Worker initialized; listener registered; fallback timer active; last scheduler cycle completed recently or active batch progress is fresh; no latched integrity error. Report these separately from RPC freshness. A fresh RPC response cannot mask a stopped worker.
6. Last indexed block/hash/timestamp and canonical hash match. Snapshot eligible target height once for the diagnostic and wait, with bounded timeout, until checkpoint reaches that target. This avoids chasing a continually moving head. Zero indexed blocks is initialization/pending, not success unless no deployment block is yet eligible; report that explicitly.
7. Report event/escrow counts, last journal position, catch-up status, and lag. Zero escrow rows is valid after fresh deployment; table population is not required without actual EscrowCreated logs.
8. Where events exist, read the most recent journal/projection relationship consistently and validate basic coherence. This is a spot check, not a proof of every record. Mandatory demo/smoke provides a real write-path probe.

Default wait timeout 30 seconds, configurable. An initializing/not-yet-eligible deployment may produce WARN diagnostics, but readiness command exits nonzero until the required usable-snapshot checks pass. Syncing beyond the captured target or unconfirmed latest blocks may be reported without calling those blocks finalized.

Add /health fields/components: databaseReady/schemaVersion, workerState (starting/idle/running/stopped/failed), listenerRegistered, fallbackTimerActive, lastCycleCompletedAt, activeBatchStartedAt, lastProgressAt, journalEventCount, escrowCount. Track progress rather than declaring every long catch-up stalled after 30 seconds. If no cycle completes and no real progress occurs within configurable WORKER_STALE_AFTER_SECONDS (default 30), degrade health and escrow endpoints to 503. Intentional idle waiting remains healthy when periodic successful cycles refresh heartbeat. Existing RPC stale behavior remains independent.

Expected terminal output must be documented with an illustrative example, explicitly marked as an example rather than fabricated evidence. Healthcheck logs contain no secrets. Supervisor waits for full readiness before reporting local startup successful and prints separate commands for healthcheck, smoke, demo, and stopping the system.
